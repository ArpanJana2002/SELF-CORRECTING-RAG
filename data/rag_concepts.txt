Retrieval-Augmented Generation (RAG) combines a retriever (typically a vector database
searched via embedding similarity) with a generator (an LLM) so that the model's answers
are grounded in an external knowledge base rather than relying solely on parametric
memory learned during training.

A standard RAG pipeline: (1) split source documents into chunks, (2) embed each chunk
with an embedding model, (3) store the embeddings in a vector index such as Chroma,
FAISS, Pinecone, or Weaviate, (4) at query time, embed the user's question and retrieve
the top-k most similar chunks, (5) pass those chunks as context to the LLM along with
the question, and (6) return the generated answer.

Plain RAG has known failure modes: the retriever may return irrelevant chunks (hurting
answer quality), or the generator may "hallucinate" facts not actually present in the
retrieved context, or the retrieved context may simply be missing from the knowledge
base entirely (e.g., the answer requires very recent information). Self-correcting RAG
architectures address these failure modes by adding grading/critique steps and fallback
retrieval paths (such as web search) directly into the pipeline, rather than assuming
the first retrieval attempt is good enough.

Common vector stores used in RAG systems include Chroma (lightweight, local-first),
FAISS (fast, in-memory, from Meta), Pinecone and Weaviate (managed, cloud), and pgvector
(Postgres extension). Common embedding models include OpenAI's text-embedding-3-small,
Cohere's embed models, and open-source sentence-transformers models such as
all-MiniLM-L6-v2, which can run entirely locally on CPU.
